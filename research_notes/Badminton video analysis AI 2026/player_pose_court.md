# Player Detection, Tracking/ReID, Pose Estimation & Court Calibration for Badminton (2025 – Oct 2026)

> Scope note: covers the four building blocks only (player detection, MOT/ReID, human pose, court detection/calibration). Shuttle tracking and stroke classification are out of scope. Project context: fixed DJI ultrawide camera behind the baseline in a multi-court hall; current stack = YOLO11 + BoT-SORT + court-polygon gating + RTMPose-m (MPS/CoreML) + auto court-corner detection with manual 4-corner correction + DJI undistortion; runtime = M4 Max, PyTorch MPS primary, CoreML for hot fixed-shape models, no MLX; any license OK except "no license grant".
>
> Research-environment caveat: arxiv.org, huggingface.co, docs.ultralytics.com, rfdetr.roboflow.com and alphaxiv.org were blocked for direct fetching in this session (proxy 403). ## Detection: what's new beyond YOLO11, and does it matter for detecting 2–4 players in a hall?

### Takeaway
Since 2024 the frontier moved to NMS-free / DETR-style real-time detectors (Ultralytics YOLO26, Roboflow RF-DETR, DEIMv2, RT-DETRv4, D-FINE/DEIM lineage) that gain roughly +1–5 COCO AP at equal latency, mostly on medium/large objects. For 2–4 full-size people on one court these COCO gains are close to irrelevant; the practical wins are (1) YOLO26's NMS-free end-to-end graph (cleaner CoreML export, no duplicate boxes, drop-in for the existing Ultralytics/AGPL stack) and (2) RF-DETR as an Apache-2.0 alternative with an official native CoreML export path — both worth only a quick A/B on own footage (far-court recall, partial occlusion by net/other players), not a re-architecture.

### Cited Findings
**Ultralytics YOLO26 (released Jan 2026; announced earlier)**
- COCO 640px table (Ultralytics self-reported): YOLO26n 40.9 mAP (40.1 end-to-end), s 48.6 (47.8), m 53.1 (52.5), l 55.0 (54.4), x 57.5 (56.9); T4 TensorRT10 latency 1.7 / 2.5 / 4.7 / 6.2 / 11.8 ms; CPU ONNX 38.9 / 87.2 / 220.0 / 286.2 / 525.8 ms; params 2.4 / 9.5 / 20.4 / 24.8 / 55.7 M — [Ultralytics GitHub README](https://github.com/ultralytics/ultralytics); range "40.9–57.5 mAP at 1.7–11.8 ms" restated in [Ultralytics YOLO26 docs](https://docs.ultralytics.com/models/yolo26/).
- Design: natively end-to-end / NMS-free by default; Distribution Focal Loss (DFL) removed to simplify the head and export — [Ultralytics YOLO26 docs](https://docs.ultralytics.com/models/yolo26/).
- Claimed up to 43% faster CPU ONNX inference for YOLO26n vs YOLO11n (Intel Xeon) — [YOLO26 analysis, arXiv 2601.12882](https://arxiv.org/pdf/2601.12882). This review states it is a *secondary* analysis based exclusively on Ultralytics' public documentation/benchmarks, i.e., **not independent verification** — [arXiv 2601.12882](https://arxiv.org/html/2601.12882v1).
- Release date conflict: Ultralytics comparison page lists 2026-01-14 — [YOLOv5 vs YOLO26](https://docs.ultralytics.com/compare/yolov5-vs-yolo26); one arXiv review version says September 2025, another January 2026 — [YOLO evolution review, arXiv 2510.09653](https://arxiv.org/pdf/2510.09653). (Most likely: announced Sept 2025, GA Jan 2026 — inference.)
- An official-looking paper "Ultralytics YOLO26: Unified Real-Time End-to-End Vision Models" (arXiv 2606.03748) is indexed by an aggregator with garbled metrics; low confidence — [opentrain.ai listing](https://www.opentrain.ai/papers/ultralytics-yolo26-unified-real-time-end-to-end-vision-models--arxiv-2606.03748/).
- YOLO27 is listed on the Ultralytics README as "Coming Soon", still in final R&D, not available, no launch date (as of the page fetched Oct 2026) — [Ultralytics GitHub](https://github.com/ultralytics/ultralytics).
- License: AGPL-3.0 or Ultralytics Enterprise License — [Ultralytics GitHub](https://github.com/ultralytics/ultralytics).

**Roboflow RF-DETR (ICLR 2026; arXiv 2511.09554, Nov 2025)**
- Neural-architecture-search DETR with DINOv2 backbone lineage; RF-DETR-N 48.0 AP on COCO, +5.3 AP over D-FINE-N at similar latency; RF-DETR-2XL is "the first real-time detector to surpass 60 AP on COCO" — [arXiv 2511.09554](https://arxiv.org/abs/2511.09554v1).
- README table (COCO AP50:95, T4 TensorRT FP16, bs=1): N 48.4 @ 2.3 ms (30.5 M, 384px), S 53.0 @ 3.5 ms, M 54.7 @ 4.4 ms, L 56.5 @ 6.8 ms (33.9 M, 704px), XL 58.6 @ 11.5 ms (126.4 M), 2XL 60.1 @ 17.2 ms; also Atto/Femto/Pico 30.5/37.8/41.6 AP — [roboflow/rf-detr README](https://github.com/roboflow/rf-detr).
- RF100-VL (real-world fine-tuning transfer benchmark) AP50:95: N 57.7, S 60.2, M 61.2, L 62.2, 2XL 63.2; SAM 3 quoted at 61.6 (number copied from the SAM 3 paper, not re-measured) — [roboflow/rf-detr README](https://github.com/roboflow/rf-detr).
- License split: `rfdetr` code and N/S/M/L detection weights + all segmentation weights = Apache-2.0; XL, 2XL and Atto/Femto/Pico = PML 1.0 via `rfdetr[plus]` — [roboflow/rf-detr README](https://github.com/roboflow/rf-detr).
- Also ships instance segmentation (Seg-N 40.3 → Seg-2XL 49.9 mask AP) and a "Keypoint Preview" model (see Pose section) — [roboflow/rf-detr README](https://github.com/roboflow/rf-detr).

**DEIMv2 (arXiv 2509.20787, Sept 2025; Intellindust AI Lab + Xiamen Univ.)**
- "Real-Time Object Detection Meets DINOv3": X 57.8 AP @ 50.3 M params, L 56.0, M 53.0, S 50.9 (first sub-10 M model > 50 AP), N 43.0, Pico 38.5 @ 1.5 M — [DEIMv2 GitHub](https://github.com/Intellindust-AI-Lab/DEIMv2); [arXiv 2509.20787](https://arxiv.org/pdf/2509.20787).
- S/M/L/X use DINOv3-derived backbones (L/X: DINOv3-S/S+; S/M: ViT-Tiny distilled from DINOv3-S); small variants use pruned HGNetv2 — [DEIMv2 GitHub](https://github.com/Intellindust-AI-Lab/DEIMv2).
- A third-party review notes the gains come mainly from medium/large objects; small-object AP stays roughly the same — [Moonlight review](https://www.themoonlight.io/review/real-time-object-detection-meets-dinov3).
- License: a custom "DEIMv2 License" (not a standard OSS license), commercial inquiries by email; FLOPs were recalculated in a May 2026 changelog because attention FLOPs had been omitted — [DEIMv2 GitHub](https://github.com/Intellindust-AI-Lab/DEIMv2).

**RT-DETRv4 (arXiv 2510.25257, Oct 2025)**
- Distills vision-foundation-model (e.g., DINOv3) semantics into lightweight real-time DETRs via a "Deep Semantic Injector" + "Gradient-guided Adaptive Modulation"; no extra inference cost; COCO AP 49.7 / 53.5 / 55.4 / 57.0 at 273 / 169 / 124 / 78 FPS — [arXiv 2510.25257](https://arxiv.org/abs/2510.25257v1). Baseline context: original RT-DETR-R50 53.1 AP @ 108 FPS (2023, earlier) — [RT-DETR arXiv 2304.08069](https://arxiv.org/abs/2304.08069v3).

**Racket-sport practice (what papers actually use for players)**
- A Nov 2025 tennis pipeline still uses YOLOv8 for player detection (plus YOLOv5 ball, ResNet50 court keypoints) — [arXiv 2511.04126](https://arxiv.org/abs/2511.04126v1).
- A 2025 broadcast-badminton method (BST) reuses off-the-shelf pose, shuttle and court-line models rather than proposing a new player detector — [arXiv 2502.21085](https://arxiv.org/abs/2502.21085v3).
- Padel pipelines (2024–2026) likewise use YOLOv8 + ByteTrack for players — [ULL thesis](https://riull.ull.es/xmlui/handle/915/42735); [padex on PyPI](https://pypi.org/project/padex/).

### Inferences
- In a singles court shot from behind the baseline, the near player is large and the far player is medium-sized; COCO-AP deltas of 1–5 points (concentrated on medium/large objects) are unlikely to change player recall materially. The failure modes that matter in this setting (partial occlusion by net posts/neighbouring players, far-court players at the distorted image edge after undistortion, umpires/spectators near the polygon) are not what COCO AP measures — evaluate on 200–500 labelled frames of club footage instead.
- YOLO26 is the lowest-effort upgrade: same Ultralytics API/license already accepted, NMS-free graph removes a post-processing step that is awkward in CoreML, and pose/seg heads share the same family. Expected benefit: modest; risk: low.
- RF-DETR-S/M is the strongest permissively licensed alternative if YOLO26 shows misses; its RF100-VL scores suggest better fine-tuning transfer to niche domains, which matters if a club-specific detector is ever fine-tuned. DEIMv2 and RT-DETRv4 bring custom/DINOv3-derived license terms and TensorRT-centric tooling with no Apple notes — low priority here.
- Detection-level court gating stays necessary regardless of detector; no 2025–2026 work removes the need to reject neighbouring-court players.

### Gaps
- No independent (non-vendor) benchmark of YOLO26 vs YOLO11 vs RF-DETR on indoor-sports person detection was found; all numbers are vendor/author self-reported COCO/RF100-VL.
- No measured MPS/CoreML latency on M4 Max for any of these detectors was found (only a claimed iPhone figure for YOLO26, see portability section).
- Could not fetch the YOLO26 arXiv paper or RF-DETR paper full text (arXiv blocked); small-object AP breakdowns not verified.

## Tracking / ReID: sports MOT advances 2025–2026 and what keeps identities stable

### Takeaway
2025–2026 sports-MOT progress came from three directions: (1) learned, multi-cue association (CAMELTrack, Apache-2.0, ~80 HOTA SportsMOT), (2) mask-propagation cues from video segmentation models (McByte → McByte++, SAM2MOT, SAM 3-based "selective mask propagation" claiming ~87 HOTA SportsMOT), and (3) offline tracklet split/merge with ReID embeddings (GTA, MIT). For a clip-upload (offline) badminton pipeline with only 2–4 gated players, the cheapest high-value additions to BoT-SORT are an offline global tracklet-association pass (GTA-style) plus court-half/role priors; mask-propagation trackers add robustness at crossings (doubles) but at large compute cost and with immature Apple-Silicon support.

### Cited Findings
**Independent unified benchmark (most trustworthy comparison found)**
- Roboflow `trackers` (Apache-2.0) re-ran trackers with default parameters on standard splits (YOLOX detections; oracle GT boxes for SoccerNet), HOTA: SportsMOT — SORT 70.8, ByteTrack 73.0, OC-SORT 71.7, **BoT-SORT 73.8**, C-BIoU 73.1, **McByte 76.5**; DanceTrack — BoT-SORT 57.8, McByte 67.2; SoccerNet — BoT-SORT 84.5, McByte 85.0. No ReID branches included in this benchmark — [roboflow/trackers README](https://github.com/roboflow/trackers). Note: Roboflow's McByte docs say some McByte figures came from the author's PR — [Roboflow McByte docs](https://trackers.roboflow.com/develop/trackers/mcbyte/).

**Learned association**
- CAMELTrack (EPFL/UCLouvain, arXiv 2505.01257, May 2025): learned cue-agnostic association module for online tracking-by-detection, trainable in < 1 h on one GPU; self-reported HOTA DanceTrack 69.3, SportsMOT 80.4 — [arXiv 2505.01257](https://arxiv.org/html/2505.01257v1). README: SportsMOT 80.3 (appearance + keypoints), DanceTrack 66.1 (appearance only) / 69.3 (appearance + keypoints), MOT17 62.4, PoseTrack21 66.0, BEE24 50.3; Apache-2.0; per-dataset + global checkpoints on Hugging Face; built on TrackLab; detector YOLOX; "Release of the SOTA weights" and code cleanup still listed as upcoming; no venue named; no FPS given — [CAMELTrack GitHub](https://github.com/TrackingLaboratory/CAMELTrack).
- MOTIP (CVPR 2025, "MOT as ID Prediction", end-to-end): DanceTrack 67.5 HOTA / 57.6 AssA; SportsMOT 71.9 HOTA / 62.0 AssA / 75.0 IDF1 (arXiv table) — [CVPR 2025 paper](https://openaccess.thecvf.com/content/CVPR2025/html/Gao_Multiple_Object_Tracking_as_ID_Prediction_CVPR_2025_paper.html); [arXiv 2403.16848](https://arxiv.org/pdf/2403.16848).
- NOOUGAT (NVIDIA + TU Munich, arXiv 2509.02111, Sept 2025): GNN over non-overlapping subclips + autoregressive long-term layer; one model runs online or offline, subclip size trades latency vs context; +9.2 online AssA on SportsMOT, more offline; absolute HOTA not found in snippet — [arXiv 2509.02111](https://arxiv.org/abs/2509.02111v1). A 2026 preprint lists NOOUGAT at 85.6 HOTA on SportsMOT — [arXiv 2606.13033](https://arxiv.org/pdf/2606.13033).
- SportMamba (arXiv 2506.03335, 2025): state-space motion model for team sports; +1.06 HOTA / +1.6 IDF1 over DiffMOT on SportsMOT; note DiffMOT is listed as 72.1 HOTA in SportMamba's table but 76.2 elsewhere (conflict) — [arXiv 2506.03335](https://arxiv.org/pdf/2506.03335).
- TrackTrack (KAIST, CVPR 2025): track-perspective association + track-aware initialization; evaluated MOT17/MOT20/DanceTrack (not SportsMOT); code public with YOLOX + FastReID — [CVPR 2025 entry](https://mlanthology.org/cvpr/2025/shim2025cvpr-focusing); [TrackTrack GitHub](https://github.com/kamkyu94/TrackTrack).

**Mask-propagation / segmentation-foundation-model trackers**
- McByte (Inria, CVPR 2025 Workshops — CVSports): adds a temporally propagated segmentation mask as association cue; no training, no per-video tuning; evaluated on SportsMOT, DanceTrack, SoccerNet-tracking 2022, MOT17 — [CVPRW 2025](https://openaccess.thecvf.com/content/CVPR2025W/CVSPORTS/html/Stanczyk_No_Train_Yet_Gain_Towards_Generic_Multi-Object_Tracking_in_Sports_CVPRW_2025_paper.html). Code MIT; YOLOX-X SportsMOT detector; Cutie for mask propagation; GPU-memory knob `max_internal_size` (halving 1080→540 cuts cost ~4×, with accuracy loss on small objects) — [McByte GitHub](https://github.com/tstanczyk95/McByte). Masks only used for ambiguous matches; SAM init + Cutie propagation; off by default in Roboflow's port — [Roboflow McByte docs](https://trackers.roboflow.com/develop/trackers/mcbyte/). Aggregator-listed (unverified) SportsMOT HOTA 76.9 test — [arXiv 2506.01373 via search](https://arxiv.org/abs/2506.01373).
- McByte++ (arXiv 2608.15688, Aug 2026, "Training-Free Long-Term MOT for Sports Video Analytics"): lightweight mask propagation + conditional camera-motion compensation + online ReID; up to +3.0 HOTA / +6.1 IDF1 over McByte online on SoccerNet-tracking and SportsMOT, more with offline global association; up to an order of magnitude faster; no detector retraining; code "will be released" — [arXiv 2608.15688](https://arxiv.org/pdf/2608.15688).
- SAM 3 (Meta, released 2025-11-19): detects/segments/tracks all instances of a text- or exemplar-prompted concept in images and video; 848 M params; decoupled detector–tracker sharing a vision encoder; video results reported on SA-V/YT-Temporal/SmartGlasses/LVVIS (e.g., LVVIS HOTA 44.5), **no standard MOT (SportsMOT etc.) numbers**; install requires CUDA ≥ 12.6, Python ≥ 3.12, PyTorch ≥ 2.7; SAM License — [facebookresearch/sam3](https://github.com/facebookresearch/sam3); release date — [aifilms blog](https://studio.aifilms.ai/blog/meta-sam3-text-segmentation-tracking).
- SAM 3.1 "Object Multiplex" (2026-03-27): shared-memory joint multi-object tracking, "significantly faster without sacrificing accuracy" — [facebookresearch/sam3](https://github.com/facebookresearch/sam3); ~7× faster at 128 objects on one H100 per a third-party blog (unverified) — [Labellerr](https://www.labellerr.com/blog/sam-3-vs-sam-3-1-performance-comparison/).
- "Selective Mask Propagation for MOT" (A. Holmberg, arXiv 2606.13033, June 2026): training-free; base tracker (Deep-EIoU) hands off to a VOS model (SAM 3) only when an assignment-uncertainty signal fires; SAM3-Deep-EIoU + global association: SportsMOT test 87.2 HOTA / 84.2 AssA / 93.6 IDF1 / 98.1 MOTA (abstract says 86.8 — unresolved discrepancy) vs Deep-EIoU 77.2 and GTA 81.0; val ablation +1.5 HOTA from selective propagation, 88.5 HOTA with GTA — [arXiv 2606.13033](https://arxiv.org/pdf/2606.13033); [wizwand listing](https://www.wizwand.com/paper/6a2b92bfd33dfb23e783b1d4). Single-author preprint, no independent reproduction found.
- SAM2MOT (arXiv 2504.04519 → AAAI 2026): tracking-by-segmentation extending SAM 2 to MOT, zero-shot (pretrained detector + segmentor), boxes from masks; +2.1 HOTA / +4.5 IDF1 on DanceTrack over prior methods; cross-object-interaction module most important for occlusions; code github.com/TripleJoy/SAM2MOT — [arXiv 2504.04519](https://arxiv.org/abs/2504.04519v5); [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/37455).

**Offline tracklet refinement / ReID**
- GTA — Global Tracklet Association (ACCV 2024 workshop; earlier than window but key): model-agnostic offline post-processing; Splitter (DBSCAN on each tracklet's embeddings → split ID-switched tracklets) + Connector (merge by mean cosine distance); +10.24% HOTA for SORT and +3.83% for Deep-EIoU, reaching 81.04 HOTA on SportsMOT — [arXiv 2411.08216](https://arxiv.org/pdf/2411.08216). Code MIT; ReID = OSNet (torchreid) trained on SportsMOT; needs tuning of `eps`, `min_samples`, `merge_dist_thres`; tested PyTorch 2.3/CUDA 11.8 — [gta-link GitHub](https://github.com/sjc042/gta-link).
- Deep-EIoU (WACV 2024 workshop, earlier baseline): 77.2 HOTA / 79.8 IDF1 / 67.7 AssA on SportsMOT, Kalman-free, iterative scale-up expansion IoU + deep features — [arXiv 2306.13074](https://arxiv.org/pdf/2306.13074). Re-confirmed Oct 2026: repo has **no LICENSE file or license declaration** — [Deep-EIoU GitHub](https://github.com/hsiangwei0903/Deep-EIoU).

**Benchmarks/challenges context**
- SportsMOT covers basketball, football/soccer, volleyball — no racket sports — [SportsMOT arXiv 2304.05170](https://arxiv.org/pdf/2304.05170); [NOOUGAT summary](https://arxiv.org/abs/2509.02111v1).
- SoccerNet 2025 ran four tasks: Team Ball Action Spotting, Monocular Depth Estimation, Multi-View Foul Recognition, Game State Reconstruction (GSR, metric GS-HOTA: positions on 2D pitch + role + jersey + team) — [SoccerNet 2025 results, arXiv 2508.19182](https://arxiv.org/pdf/2508.19182). The 2025 GSR winner and score could not be retrieved (aggregator shows an unattributed 61.5 GS-HOTA) — [SoccerNet GSR search results](https://arxiv.org/pdf/2404.11335).

### Inferences
- Singles badminton with court-polygon gating is a far easier MOT problem than SportsMOT (2 targets, separated by the net, rarely occluding each other). Identity errors will mostly come from: neighbouring-court players stepping into the polygon, line-judges/coaches walking past, detector drop-outs at the far baseline, and (in doubles, P3+) partner crossings. Court-half assignment ("near/far side") is a stronger identity prior than any appearance ReID in singles.
- Because clips are processed offline, a GTA-style global pass (split tracklets with mixed embeddings, then merge by appearance + court-side + temporal-gap constraints) is cheap, MIT-licensed, and directly targets ID fragmentation; it can sit after the existing BoT-SORT without replacing it.
- For **similar clothing** (club kit), appearance ReID is weak; combining (a) court half, (b) pose/keypoint cues (CAMELTrack shows keypoints add ~3 HOTA on DanceTrack: 66.1 → 69.3), and (c) motion continuity is more robust than an off-the-shelf OSNet trained on SportsMOT. CAMELTrack's Apache-2.0 + keypoint cue fits a stack that already runs RTMPose.
- **Court-side switches between games** are not a MOT problem but an identity-linking problem across long gaps: cluster per-game tracklets by ReID embedding/body-shape and confirm with a one-click user label; no 2025–2026 paper found addresses racket-sport end changes specifically.
- SAM 3-/Cutie-based mask propagation gives the best published sports-MOT numbers, but costs a segmentation model per frame (848 M-param SAM 3), is CUDA-first, and is mostly needed for dense crowds — likely over-engineering for singles; reconsider for doubles if crossings cause swaps.
- The "Selective Mask Propagation" SOTA pipeline is built on Deep-EIoU (no license grant) → the same licensing objection applies unless the base tracker is swapped (the paper says base tracker and VOS are black boxes, so BoT-SORT could substitute — untested).

### Gaps
- No 2025–2026 MOT benchmark or paper on badminton/tennis/padel players specifically was found; transfer of SportsMOT numbers to racket sports is unverified.
- TeamTrack (2024 dataset) and SAMURAI were not verified this session.
- License of the "Selective Mask Propagation" code, McByte++ code availability, and SAM2MOT's license were not confirmed.
- SoccerNet 2025 GSR winner/method not retrieved (arXiv blocked).
- No CAMELTrack/McByte runtime numbers on Apple Silicon found.

## Pose: what's new beyond RTMPose, and the accuracy/speed trade-offs for fast racket-sport motion and blur

### Takeaway
The 2D-pose frontier split into (a) heavy high-resolution foundation models (Sapiens2, Apr 2026, 0.1–5 B params, 308 keypoints, 1024×768, CUDA-first) and (b) real-time one-stage/DETR-style pose models (YOLO26-pose up to 71.6 AP, RF-DETR Keypoint Preview 71.8 AP, DETRPose up to 73.3 AP, all Apache/AGPL) that roughly match but do not clearly beat RTMPose-m's 75.8 AP top-down accuracy. RTMPose remains a sound choice, but MMPose itself looks stagnant (last tagged release Jan 2024) — `rtmlib` (Apache-2.0, ONNX, no mmcv) is the practical way to keep the RTM family. 3D: SAM 3D Body (Nov 2025, SAM License) and PromptHMR/GVHMR-style world-grounded HMR are the new state of the art but are heavy and estimate-grade; motion blur remains largely unsolved in the literature beyond synthetic-blur augmentation.

### Cited Findings
**Baselines (earlier, labelled)**
- RTMPose-m (2023): 75.8 AP COCO, 90+ FPS on i7-11700 CPU, 430+ FPS on GTX 1660 Ti; RTMPose-s 72.2 AP — [arXiv 2303.07399](https://arxiv.org/abs/2303.07399).
- ViTPose (2022) largest model 80.9 AP COCO test-dev — [arXiv 2204.12484](https://arxiv.org/pdf/2204.12484); ViTPose++ generic body pose — [arXiv 2212.04246](https://arxiv.org/pdf/2212.04246).
- Sapiens v1 (ECCV 2024): pretrained on 300 M+ human images, native 1K resolution, +7.6 mAP over prior SOTA on Humans-5K pose — [Sapiens ECCV 2024](https://www.ecva.net/papers/eccv_2024/papers_ECCV/papers/00529.pdf). On COCO-WholeBody: Sapiens-2B 79.2 body AP / 74.4 whole-body AP vs ViTPose+-H 75.9 / 61.2 (as tabulated in SDPose) — [SDPose arXiv 2509.24980](https://arxiv.org/pdf/2509.24980).
- MMPose: Apache-2.0; flagship RTMPose, RTMO (one-stage), RTMW (whole-body, m–x, 256×192 / 384×288), RTMW3D (real-time 3D whole-body); latest announced release v1.3.0 dated January 4, 2024; 306 open issues — [open-mmlab/mmpose](https://github.com/open-mmlab/mmpose).
- `rtmlib`: Apache-2.0; runs RTMPose (17/21/26/133 kpts), RTMO, DWPose, RTMW, RTMW3D, ViTPose plus YOLOX/RF-DETR/RTMDet detectors; backends opencv / onnxruntime / openvino (tensorrt mentioned); `mps` appears as a device option; "without mmcv, mmpose, mmdet"; no CoreML backend mentioned — [Tau-J/rtmlib](https://github.com/Tau-J/rtmlib).

**New 2D models (2025–2026)**
- Sapiens2 (Meta, initial release 2026-04-24; arXiv 2604.21681, listed as ICLR 2026): sizes 0.1 B / 0.4 B / 0.8 B / 1 B (1.46 B) / 1 B-4K / 5 B params; tasks = 308 whole-body keypoints, 29-part segmentation, normals, pointmaps, matting; trained at 1024×768 (4K variant 4096×3072); requires Python ≥ 3.12, PyTorch ≥ 2.7; quick-start uses `.cuda()`; optional DETR person detector; single-file `sapiens2.py` needing only torch + safetensors; no ONNX/lite variants; "Sapiens2 License" (custom) — [facebookresearch/sapiens2](https://github.com/facebookresearch/sapiens2). Pretraining combines masked reconstruction with self-distilled contrastive objectives — [HF paper listing](https://api-inference.huggingface.co/papers/2604.21681). Pose evaluated on a 10K test set with 308 keypoints (5B > 1B); exact metrics not retrievable — [arXiv 2604.21681 snippet](https://arxiv.org/pdf/2604.21681).
- YOLO26-pose (Jan 2026): COCO-Pose mAP50-95 (end-to-end) n 57.2, s 63.0, m 68.8, l 70.4, x 71.6 (640px, one-stage, NMS-free) — [Ultralytics GitHub](https://github.com/ultralytics/ultralytics).
- RF-DETR Keypoint Preview: 71.8 AP50:95 (OKS), 9.7 ms T4, 40.7 M params, 576px, Apache-2.0, COCO person keypoints; README compares against YOLO11-pose and YOLO26-pose — [roboflow/rf-detr](https://github.com/roboflow/rf-detr).
- DETRPose (Univ. New Mexico, arXiv 2506.13027, June 2025): RT-DETR hybrid encoder + D-FINE decoder, Pose-LQE head, keypoint-similarity varifocal loss; trains with 5–10× fewer epochs — [arXiv 2506.13027](https://arxiv.org/html/2506.13027v1). COCO val AP N 57.2 / S 67.0 / M 69.4 / L 72.5 / X 73.3 (test-dev 56.7–72.2); CrowdPose test 56.0–75.1; latency 2.8–13.3 ms on V100 TensorRT fp16; Apache-2.0; ONNX/TensorRT export scripts; weights on GitHub releases + HF (July 2026) — [DETRPose GitHub](https://github.com/SebastianJanampa/DETRPose).
- SDPose (arXiv 2509.24980, 2025): exploits diffusion priors for out-of-domain / robust pose estimation (relevant to unusual viewpoints/blur, but heavy) — [arXiv 2509.24980](https://arxiv.org/pdf/2509.24980).

**3D pose lifting & mesh recovery**
- SAM 3D Body (Meta; checkpoints released 2025-11-19, arXiv 2602.15989, Feb 2026): promptable single-image full-body HMR (body, feet, hands) on the Momentum Human Rig (MHR); optional 2D-keypoint/mask prompts; backbones DINOv3-H+ (840 M) / ViT-H (631 M); 3DPW MPJPE 54.8, EMDB MPJPE 61.7–62.9, RICH PVE 60.3–61.7, COCO PCK@.05 86.5–86.8; **single-image only** (no temporal model stated); no speed/hardware/MPS notes; SAM License for code and checkpoints — [facebookresearch/sam-3d-body](https://github.com/facebookresearch/sam-3d-body); [arXiv 2602.15989](https://arxiv.org/abs/2602.15989). SAM License permits redistribution with pass-through terms and prohibits military/weapons uses (per a mirror's summary) — [HF mirror](https://huggingface.co/LibreYOLO/LibreSAM3DBodyh-mesh).
- PromptHMR (May 2025): PromptHMR-Vid reports EMDB-2 world-aligned MPJPE 71.0 mm, foot skating 3.5 mm, using metric SLAM + monocular depth; GVHMR (SIGGRAPH Asia 2024, earlier) 111.0 mm WA-MPJPE on EMDB-2 vs WHAM 135.6; WATCH (arXiv 2509.04600, 2025) 3DPW PA-MPJPE 35.4 / MPJPE 54.5 vs GVHMR 36.2 / 55.6 — protocols differ across papers (PromptHMR uses DINOv2 + GT focal length), so not directly comparable — [WATCH arXiv 2509.04600](https://arxiv.org/pdf/2509.04600); GVHMR code public — [gvhmr on PyPI](https://pypi.org/project/gvhmr/).
- CameraHMR (3DV 2025): estimates camera FoV and conditions HMR 2.0 on it; dense surface keypoints for better shape; code and pseudo-GT "for research purposes" — [CameraHMR project](https://camerahmr.is.tue.mpg.de); [arXiv 2411.08128](https://arxiv.org/pdf/2411.08128).
- KASportsFormer (arXiv 2507.20763, July 2025): kinematic-anatomy-enhanced transformer lifter for short sports clips (27-frame windows); MPJPE 58.0 mm SportsPose, 34.3 mm WorldPose; code + models on GitHub (jw0r1n/KASportsFormer); preprint, no independent reproduction found — [arXiv 2507.20763](https://arxiv.org/pdf/2507.20763).

**Fast motion / blur / racket-sport evidence**
- Baseball pitch analysis: partial-body motion blur in 30 fps broadcast video; synthetic blur augmentation improved existing pose estimators by 29.2% on average (3D-focused) — [Mitigating Motion Blur… Baseball](https://astro.paperswithcode.com/paper/mitigating-motion-blur-for-robust-3d-baseball).
- ICCV 2025 (Kim, Cho, Yoon): extreme-blur 2D pose via event-camera domain adaptation (needs event sensor; not applicable to DJI RGB) — [ICCV 2025 entry](https://mlanthology.org/iccv/2025/kim2025iccv-sharp/).
- IMPose (arXiv 2606.04480, 2026): interactive multi-person pose correction; under motion blur propagates corrected keypoints for 34.02 frames on average vs CoTracker 21.89 — [arXiv 2606.04480](https://arxiv.org/pdf/2606.04480).
- Ice-hockey broadcast study notes fast sports produce heavy blur/occlusion that degrade 2D estimators (date unconfirmed) — [VSL hockey study](https://openjournals.uwaterloo.ca/index.php/vsl/article/view/5866).
- RacketVision (arXiv 2511.17045, Nov 2025): multi-racket-sport benchmark (tennis, badminton, table tennis) for ball + **racket** keypoints; RTMPose top-down baseline reaches ~88.5% PCK on badminton racket keypoints (racket, not body) — [arXiv 2511.17045](https://arxiv.org/pdf/2511.17045).
- Badminton data: BFMD (arXiv 2603.25533, 2026) — 19 broadcast matches, singles+doubles, 20+ h, 1,687 rallies, 16,751 hits, with player pose keypoints — [arXiv 2603.25533](https://arxiv.org/abs/2603.25533); a Mendeley frame-level badminton movement dataset (884 videos, smartphone/camera, June 2026) — [Mendeley Data](https://data.mendeley.com/datasets/3sp4xntp34/1); doubles control-area estimation from top/back drone views using pose (2023, earlier) — [arXiv 2305.04247](https://ar5iv.labs.arxiv.org/html/2305.04247).
- No head-to-head body-pose comparison (RTMPose vs ViTPose vs MediaPipe) on badminton/tennis players was found; in sport climbing ViTPose beat MediaPipe (86.6% vs 83.5%) with YOLOv8-pose lowest — [arXiv 2505.12854](https://arxiv.org/pdf/2505.12854).

### Inferences
- For 17-keypoint body pose on 2 players, RTMPose-m (75.8 AP) is still at or above the new real-time one-stage models (YOLO26-pose-l 70.4, RF-DETR-KP 71.8, DETRPose-L 72.5); there is no 2025–2026 real-time model that clearly justifies replacing it on accuracy. A switch to YOLO26-pose would be motivated by pipeline simplicity (one model for boxes + keypoints, NMS-free CoreML), not accuracy.
- The upgrade path with real accuracy upside is a larger top-down model (RTMW-l/x 384×288 or ViTPose-L/H via rtmlib, Sapiens2-0.4B offline) applied only to the 2–4 gated player crops — feasible offline on an M4 Max, but Sapiens2 is CUDA-first and would need MPS validation (fp32, NaN check vs CPU per project rules).
- Fast racket motion: wrists/racket-arm keypoints during smashes are the most blur-affected; the evidence suggests (a) higher capture fps/shorter shutter on the DJI, (b) temporal smoothing/lifting (KASportsFormer-like 27-frame windows) and (c) synthetic-blur fine-tuning help more than swapping the per-frame model. Treat wrist-derived metrics (e.g., racket-arm speed) as estimates.
- 3D: SAM 3D Body / PromptHMR are research-grade, single-image or SLAM-dependent and heavy; a fixed calibrated camera with a known court plane makes simpler 2D→3D lifting plus ground-plane foot anchoring sufficient for positional analytics. Any 3D joint angle should carry an uncertainty label ("Schätzung").

### Gaps
- Sapiens2 pose benchmark numbers (COCO / 308-kpt test) and its license terms in detail could not be retrieved; whether Sapiens2 runs on MPS is unknown.
- No published per-joint accuracy under motion blur for RTMPose/RTMW vs ViTPose vs Sapiens on racket sports.
- No racket-sport-specific 3D lifting benchmark found (SportsPose/WorldPose are closest).
- RTMO/RTMW release dates and any post-2024 MMPose releases not confirmed (page shows only Jan 2024).
- SAM 3D Body inference speed / memory unknown.

## Court detection & calibration: 2025–2026 methods, lens distortion, automatic multi-court selection

### Takeaway
Sports-field registration research remains soccer-dominated (PnLCalib/NBJW, TVCalib, SoccerNet 2023 winners); SoccerNet dropped the calibration challenge in 2025. Racket-sport court detection is still mostly keypoint-heatmap networks + homography refinement (TennisCourtDetector-style, ResNet50 keypoints) or classical line models, with no dedicated 2025–2026 badminton court detector with public weights and a clear license found. The most useful new piece for this project is single-image intrinsic/distortion estimation (AnyCalib, ICCV 2025) as a check/initializer for the DJI ultrawide undistortion; automatic selection of the target court among several in a hall has no published method — the locked decision (auto-detect + user picks court + 4-corner correction) is still the state of practice.

### Cited Findings
**Soccer field registration (method source for racket sports)**
- PnLCalib (Gutiérrez-Pérez & Agudo; arXiv 2404.08401; accepted Computer Vision and Image Understanding): keypoint + line detection with a 3D field model; non-linear points-and-lines refinement optimizing camera pose with K fixed; evaluated SoccerNet-Calibration, WorldCup 2014, TS-WorldCup — [arXiv 2404.08401](https://arxiv.org/pdf/2404.08401). Repo: GPL-2.0; single- and multi-view keypoint/line weights released (v1.0.0), fine-tuned variants for WC14/TSWC/WorldPose; **lens-distortion optimization added 2026-03-10** (`utils/utils_calib_wp.py`); soccer-specific template, no custom-template guidance — [PnLCalib GitHub](https://github.com/mguti97/PnLCalib).
- "No Bells, Just Whistles" (NBJW, earlier version of same arXiv ID): DLT calibration from SoccerNet-derived keypoints, no refinement — [sotaverified summary](https://sotaverified.org/papers/no-bells-just-whistles-sports-field).
- TVCalib (WACV 2023, earlier): estimates position, rotation, focal length and optional radial distortion without keypoint correspondences — [arXiv 2207.11709](https://arxiv.org/pdf/2207.11709).
- SoccerNet 2025 had no camera-calibration task (only Team Ball Action Spotting, Monocular Depth, MV-Foul, GSR); 2025 reports describe GSR calibration pipelines as landmark detection + homography using NBJW, PnLCalib, Broadtrack — [SoccerNet 2025 results](https://arxiv.org/pdf/2508.19182). Last calibration challenge winner found: Sportlight (Falaleev et al., 2023), keypoints + lines, combined metric 0.55 — [SoccerNet 2023 results](https://arxiv.org/pdf/2309.06006); follow-up "Enhancing Soccer Camera Calibration Through Keypoint Exploitation" (2024) — [arXiv 2410.07401](https://arxiv.org/html/2410.07401v1).

**Racket-sport court detection**
- TennisCourtDetector (earlier, ~2023): TrackNet-like heatmap net, 640×360 input, 14 keypoints + centre channel; post-processing with classical line intersections + homography to a reference court fixes occluded points; precision 0.963 / accuracy 0.961 / median error 1.83 px (≤ 7 px threshold) with refinement + homography vs 0.936 / 0.933 / 2.83 px base; ~8,841 images (hard/clay/grass); weights on Google Drive; **no license** — [TennisCourtDetector GitHub](https://github.com/yastrebksv/TennisCourtDetector).
- Tennis 2025: ResNet50-based court-keypoint model in a full player/ball pipeline, "robust in varying court conditions" (self-reported) — [arXiv 2511.04126](https://arxiv.org/abs/2511.04126v1). Amateur-footage tennis line detection (2024, earlier): targets low camera angles, shadows, worn lines, builds on a homography method — [arXiv 2404.06977](https://arxiv.org/pdf/2404.06977). ML6 notes Hough-based methods work for some courts but are hard to generalize; their CNN predicts 16 line-intersection keypoints — [ML6 blog](https://www.ml6.eu/en/blog/improving-tennis-court-line-detection-with-machine-learning).
- Badminton: hit-frame detection pipeline (2023) trains a "Court R-CNN" for court keypoints, used to filter non-player detections; MIT-licensed repo with checkpoints on Google Drive (court-model inclusion unconfirmed) — [arXiv 2307.16000](https://arxiv.org/pdf/2307.16000). MonoTrack (2022) court detection = model-based Farin et al. algorithm + graph-based modification — [arXiv 2204.01899](https://arxiv.org/pdf/2204.01899). BST (2025) uses an existing court-line detector to locate players on court — [arXiv 2502.21085](https://arxiv.org/abs/2502.21085v3).
- Padel: monocular padel 2D tracking with court detection + homography (IDEAL 2024, Springer 2025) — [URJC repository](https://burjcdigital.urjc.es/handle/10115/42210); `padex` package lists court-line detection + homography calibration, public weights still on roadmap — [padex PyPI](https://pypi.org/project/padex/); PadelTracker100 dataset (~100k frames, player positions + pose, Data in Brief, Feb 2026) — [PMC article](https://pmc.ncbi.nlm.nih.gov/articles/PMC12926558/) (attribution of this URL to PadelTracker100 inferred from search context).

**Lens distortion / intrinsics**
- AnyCalib (Tirado-Garín & Civera, ICCV 2025): model-agnostic single-view calibration; regresses per-pixel ray directions, closed-form recovery of intrinsics for pinhole, Brown-Conrady and Kannala-Brandt (fisheye) models; handles cropped/stretched images; code github.com/javrtg/AnyCalib; claims to beat other methods incl. 3D foundation models with less training data — [ICCV 2025](https://openaccess.thecvf.com//content/ICCV2025/html/Tirado-Garin_AnyCalib_On-Manifold_Learning_for_Model-Agnostic_Single-View_Camera_Calibration_ICCV_2025_paper.html); [ICCV poster](https://iccv.thecvf.com/virtual/2025/poster/868). Third-party demo uses a DINOv2 ViT-L/14 backbone — [HF Space demo](https://simonpick-anycalib-gpu.hf.space/).
- GeoCalib (ECCV 2024, earlier): predicts perspective fields with confidences, then Levenberg-Marquardt camera fit — [arXiv 2409.06704](https://arxiv.org/html/2409.06704v2).

**Multi-court selection**
- No 2025–2026 paper or repo was found that automatically selects one target court among several adjacent courts in a hall (searches for badminton/tennis/padel multi-court selection returned only single-court methods) — see searches cited above, e.g. [badminton court keypoint search result: hit-frame paper](https://arxiv.org/pdf/2307.16000).

### Inferences
- Badminton has more line intersections than tennis (singles/doubles side lines, short and long service lines, centre line) — a 20–30-keypoint heatmap model + RANSAC homography to the BWF template, following TennisCourtDetector's recipe, is the closest-proven design; it must be trained on own hall footage since no licensed badminton court model with weights exists. Code reuse from TennisCourtDetector is blocked (no license), but the approach is reproducible.
- Multi-sport hall floors (overlapping volleyball/basketball/handball lines in other colours) and several parallel badminton courts make "find all court quads, let the user click one" the robust approach; a cheap auto-default (court whose quad is largest/most central in the image, which for a camera behind one baseline is almost always the target court) can pre-select, with the existing manual 4-corner drag as correction.
- Order of operations stays: undistort (DJI ultrawide profile) → line/keypoint detection → homography; AnyCalib can serve as a one-time sanity check of the stored DJI distortion profile (e.g., residual line curvature) rather than per-video runtime. PnLCalib's new distortion optimization (GPL-2.0) is a reference for jointly refining distortion + pose from court lines if residual distortion is visible after the DJI profile.
- Because the camera is fixed per session, calibrate once per video (or per session) from a clean frame and verify with re-projection of all court lines; per-frame calibration is unnecessary.

### Gaps
- No public, licensed badminton court-keypoint model or benchmark (2025–2026) found; Roboflow Universe search snippets point to community badminton-court keypoint datasets (~614 images) but URL/license could not be verified.
- AnyCalib's license, accuracy on DJI ultrawide images, and PyTorch MPS compatibility not verified.
- No quantitative study of homography error vs player-position error for racket sports found.
- 2025 SoccerNet GSR calibration-component details (which calibrator the winners used) not retrieved.

## Code, weights, licenses and PyTorch MPS / CoreML / ONNX portability

### Takeaway
Everything relevant has code + weights except some 2026 preprints (McByte++ "to be released") and anything built on Deep-EIoU (no license). License red flags for this project are limited to Deep-EIoU, TennisCourtDetector (no license) and custom/source-available terms to read before use (DEIMv2 License, Sapiens2 License, SAM License, PML 1.0 for RF-DETR XL/2XL). Apple-Silicon readiness is best for Ultralytics YOLO26 (documented CoreML export, NMS-free graph) and RF-DETR (official native CoreML cookbook), acceptable for rtmlib/ONNX pose, and weakest for SAM 3 / Sapiens2 (CUDA-first install, reported MPS bugs).

- Sapiens2: Python ≥ 3.12, PyTorch ≥ 2.7, `.cuda()` quick-start, no ONNX/lite — [sapiens2 GitHub](https://github.com/facebookresearch/sapiens2).
- rtmlib: onnxruntime/opencv/openvino backends, `mps` device string present, no CoreML — [rtmlib GitHub](https://github.com/Tau-J/rtmlib).

### Inferences
- Lowest-risk modernization on M4 Max: YOLO26 (CoreML, fixed 640 or project shape, NMS-free) for detection; keep RTMPose-m via CoreML or rtmlib/ONNX Runtime (CoreML EP) for pose; add MIT/Apache-licensed offline association (GTA-style, optionally CAMELTrack) in PyTorch MPS — all compatible with the "decode once → cache frames" design.
- Anything SAM 3-based should be treated as an optional, slow, offline "repair" stage (e.g., only on ambiguous segments), validated against CPU for NaNs per project rules, not as the primary tracker.
- Custom licenses (DEIMv2, Sapiens2, SAM, PML 1.0) are acceptable under the project's non-distributed policy only if they actually grant use; they should be read once and recorded — they are not "no license" cases like Deep-EIoU/TennisCourtDetector.

- Licenses for AnyCalib, KASportsFormer, SAM2MOT, PromptHMR, GVHMR, NOOUGAT, TrackTrack, MOTIP not verified this session (GitHub API blocked; only some READMEs fetched).
